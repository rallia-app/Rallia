Protocole de test des paiements

Tournois et ligues payants · Environnement : staging · Stripe en mode test (sandbox) · 2 août 2026

Deux testeurs, deux comptes. Alex utilise demo@rallia.ca, JDL utilise jdl.sonkin+10@gmail.com. Chaque scénario indique qui le fait avec une pastille Alex ou JDL. Les deux comptes sont administrateurs sur staging, ce qui est requis pour créer un événement payant.

Le nom affiché dans l'app n'est pas ton nom. Ces deux comptes portent un profil de test : demo@rallia.ca s'affiche comme Alex Monza, et jdl.sonkin+10@gmail.com s'affiche comme Jose Caroon. C'est normal. Dans les listes de participants, cherche ces noms-là, pas le tien.

Le cycle de l'argent : l'organisateur complète son compte Stripe Connect → il publie un événement payant → le joueur s'inscrit et paie par carte → l'argent atterrit dans le solde Stripe de l'organisateur (jamais dans celui de Rallia) → il y reste jusqu'à 24 h après la fin de l'événement → un cron horaire déclenche le versement. Rallia prélève seulement des frais de service.

Les frais de service : 5 % du prix d'entrée, plafonnés à 20,00 $, plus TPS/TVQ (14,975 %) sur les frais seulement. Deux modes par événement : joueur paie (les frais s'ajoutent au montant affiché) ou organisateur absorbe (le joueur paie exactement le prix d'entrée, les frais sont retenus sur le versement). Les frais de service ne sont jamais remboursés, même sur un remboursement complet.

0. Avant de commencer

  • Utilise le build preview (pas production). Il pointe vers staging et vers Stripe en mode test.
  • Carte de test : 4242 4242 4242 4242, n'importe quelle date future, n'importe quel CVC, code postal H3T 1X8.
  • Aucune vraie carte, aucun vrai compte bancaire. Stripe affiche « You're using a test account with test data » en haut de ses écrans : si tu ne vois pas ça, arrête et signale-le.
  • Les montants sont fictifs mais les écrans sont les vrais. Prends une capture d'écran de tout ce qui te semble croche.

Deux types de fixtures. Les inscriptions déjà payées d'avance ont été créées directement en base avec de faux identifiants Stripe (pi_sim…) : elles servent à vérifier l'affichage (pastilles, montants, boutons). Toute action qui déclenche un vrai remboursement chez Stripe va échouer sur celles-là, et c'est normal. Les scénarios marqués vrai paiement sont ceux où tu paies réellement avec la carte de test : ce sont les seuls où le cycle complet (charge, webhook, remboursement) est validé.

Les montants de frais des fixtures pré-payées sont périmés. Elles ont été créées quand les frais incluaient encore un montant fixe de 1,00 $. Le tarif actuel est 5 % seulement. Sur ces inscriptions-là, les frais affichés seront donc plus élevés que le calcul de la page précédente : c'est attendu, ce n'est pas un bogue. Fie-toi aux scénarios vrai paiement pour valider le calcul des frais.

1. Onboarding Stripe Connect (à faire en premier)

Rien d'autre ne fonctionne tant que ce n'est pas fait. Un événement payant ne peut pas être publié, et personne ne peut payer pour y entrer, tant que son organisateur n'a pas complété son compte Stripe. Alex et JDL organisent chacun des événements où l'autre doit payer : les deux doivent donc compléter cette étape, sinon la moitié du protocole est bloquée.

1.1 Compléter le compte Alex JDL

  1. Ouvre un de tes propres événements payants (voir le tableau de la section 2 ou 4).
  2. Onglet Aperçu, section GÉRER : la ligne Versements affiche Action requise.
  3. Touche-la. Un navigateur s'ouvre sur connect.stripe.com.
  4. Vérification téléphonique : utilise le bouton « Use test code » (le code est 000000).
  5. Remplis ce que Stripe demande. En mode test, il propose des données bidon à chaque étape : accepte-les. Pour le compte bancaire, choisis STRIPE TEST BANK.
  6. Écran « Review and confirm » : vérifie que tout est rempli, puis Confirm.
  7. Le navigateur se ferme tout seul et te ramène dans l'app.

Résultat attendu : dans les 30 secondes, la mention Action requise disparaît de la ligne Versements. En la touchant de nouveau, tu arrives maintenant sur le tableau de bord Stripe (solde, versements, coordonnées bancaires) et non plus sur le formulaire d'inscription.

Point de vigilance connu. C'est exactement ici qu'un problème a été observé le 2 août : l'onboarding se complétait chez Stripe mais l'app restait bloquée sur « Action requise ». Si la mention ne disparaît pas après une minute, ferme et rouvre l'écran une fois. Si elle est toujours là, arrête le protocole et signale-le : tout le reste dépend de cette étape. Note l'heure exacte, ça sert à retrouver l'événement chez Stripe.

5. Ce qui n'est pas testable pour l'instant

  • Le versement final à l'organisateur. L'argent est libéré 24 h après la fin de l'événement par une tâche horaire, et seulement pour un tournoi terminé. Aucun fixture n'est dans cet état : [PAYE2E] 7 - Versement au createur est seulement fermé aux inscriptions, pas terminé. Le versement ne se vérifie donc pas dans une session de test normale.
  • Les remboursements sur les inscriptions pré-payées (pi_sim…). Ils échouent chez Stripe par construction. Utilise les scénarios vrai paiement pour valider un vrai remboursement.
  • Le paiement par lien de partage sur un tournoi payant : le parcours n'aboutit pas encore.
  • La création d'un tournoi payant depuis zéro est réservée aux administrateurs. Les deux comptes de test le sont, mais un organisateur ordinaire ne verra pas l'option.

6. Quoi noter en cas de problème

Pour chaque anomalie, note ces quatre choses. Sans elles, un bogue de paiement est très difficile à retracer.

  1. Le compte utilisé et l'heure exacte (à la minute près).
  2. Le nom exact du fixture, tel qu'écrit dans ce document.
  3. Le montant affiché à l'écran au moment du problème, et celui que tu attendais.
  4. Une capture d'écran, incluant les messages d'erreur ou les toasts.

Si un paiement reste bloqué en « en attente », ne réessaie pas plusieurs fois de suite : chaque tentative ouvre une nouvelle intention de paiement chez Stripe et rend le diagnostic plus difficile. Note-le et passe au scénario suivant.
